Your agent pipeline, as it stands

Opus plans and signs off. Cheap models on two separate usage pools do the building and checking, and scripts handle everything that doesn't need a model. The same four colours mean the same thing in every diagram.

  • Claude Pro (Opus 5.5)
  • OpenCode Go pool
  • Command Code GOAT pool
  • You, scripts and tools

Architecture

Claude runs only through the official claude CLI on your Pro login. Every other model call goes through Oh My Pi (omp), then 9router, then the right pool. When a pool is full, calls move along each role's fallback combo, shown further down, including free models where that is safe.

Milestone workflow

You touch the pipeline three times per milestone: the goal, the sign-off and the final merge. Everything in between runs on its own.

What happens to each task

Three agents build in parallel. The tests must fail on the old code before they count, the gates check tests, scope and security, and a reviewer from a different model family reads every change. Anything that fails climbs the retry chain on the right.

Profiles

One switch changes how much checking the pipeline does. Set the repo's usual profile in routing.sh, override it for a single run with PROFILE=fast .agents/runner.sh run, or for one task with profile: risky in its front matter.

ProfileUse it forWhat changes
defaultMost work, like the dashboard backlogsEverything on this page as drawn: two workers on feature, debug, data and UI tasks; senior review on risky and long tasks; one task at a time.
riskyAuth, payments, migrations, production dataEvery task is treated as high risk: two workers, the judge, Sol's senior review and your Opus sign-off. No review shortcuts, one task at a time. Uses noticeably more Opus quota.
fastPrototypes, internal tools, urgent backlogsOne worker unless a task is marked high risk, no judge, no off-peak wait, three tasks in parallel, one-minute polling, shorter pauses, and DeepSeek at high instead of xhigh effort.

When to use this pipeline

The pipeline pays off when work can be written down in advance and checked automatically. It trades speed for quality and low attention: a typical task takes 15 to 30 minutes, and a 10-task milestone a few hours. Use it when every one of these is true:

  • You can describe each change as a brief with acceptance criteria a test could check.
  • The repo has tests that run, or you're willing to add them first.
  • You have several tasks, not one, and don't need the result within the hour.
  • The main open question is how to build it, not what it should look like or do.

If any of these is false, work interactively instead: you and one strong model in a tight loop, then hand the settled, well-defined parts to the pipeline.

Harnesses compared

A harness is the program that runs the model: it gives it tools, edits files and keeps the session. Your setup uses Claude Code for Opus and Oh My Pi for everything else, with plain Pi as the fallback. The two web UIs you use, ompweb and pi-web, are closely related: ompweb is a fork of pi-web adapted for Oh My Pi. They don't change what the agent can do; they change how you work with it.

If you move to Paperclip

Paperclip replaces the runner, the task files and cron. The models, prompts, routing rules and gate scripts carry over unchanged. Keep the org flat: you are the board, and no management layer sits between the CTO and the seats.
