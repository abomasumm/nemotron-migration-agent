Architecture

Claude runs only through the official claude CLI on your Pro login. The scripts wake it when a decision is waiting, and it answers by running the kit's commands; it never calls the cheap models itself. Every other model call in the pipeline goes through Oh My Pi (omp), then 9router, then the right pool. When a pool is full, calls move along each role's fallback combo, shown further down, including free models where that is safe.

DeepSeek Harness is your workbench and control desk. You talk to it; it drafts briefs and prompts, and when you ask, it reads status or queues goals through kitctl, a wrapper that allows only a short list of kit commands. Its own chats reach 9router on a separate path (dashed), using DeepSeek on the GOAT pool so they never fill the Go window your workers depend on. Google AI Pro sits beside it for design: Nano Banana Pro mockups, and Gemini 3.8 Flash for UI specs and visual review, on its own subscription and never through 9router.

Which tool for which job

One question decides most of it: can you say in advance what “done” looks like, in a way a test can check? If yes and there are several pieces, it's pipeline work. If no, work interactively until it's settled, then brief it. If the open question is how it should look, start in the design lane on Google AI Pro.

Milestone workflow

You decide twice per milestone: which goal to run, and when to merge the result. dsh drafts the brief and, once you agree, queues it. In between, Claude is woken to plan, to handle tasks that get stuck or need sign-off, and to close the milestone, while dsh keeps you posted.

Portfolio cycle

Above the repos, dsh runs a slow cycle: a few times a day it looks at every repo and the shared budgets, and decides whether any repo should get its next goal. You decide what is in the backlog and in what order, and you merge each repo's results.

Inside each repo

Once a goal is queued, the repo runs the same milestone as a single-repo setup: Muse packs context, Claude plans, the runner builds, Claude triages and signs off, Claude wraps up. dsh doesn't take part until the goal is done or something is parked for you.

How Claude orchestrates

Claude doesn't poll. Every five minutes loop.sh runs the scheduler and then orchestrate.sh tick, which does the cheap work with scripts and checks for events. Only if one is waiting does it start claude -p, once, with a brief that covers every waiting event. Claude acts through the kit's own commands and stops.

Keeping Pro quota for decisions

Pro usage is shared with your chat and is the scarcest budget in the setup, so every wake is rationed.

  • Wakes have their own cap, 10 a day (16 on the risky profile), separate from the Opus retry cap of 2. Past the cap, events wait until the next day while tasks keep running.
  • At least 30 minutes between wakes (10 on fast), so events that arrive close together are handled in one call. A new goal skips the wait.
  • If the waiting events are exactly what Claude saw last time, no wake. An unresolved event gets one more look the next day.
  • A task that is still stuck after two triages goes to you instead of back to Claude.
  • When Pro reports a usage limit, the orchestrator backs off for an hour and that attempt doesn't count toward the cap.
  • Claude reads a prepared brief and short digests, not raw logs. It opens a diff only to sign off high-risk work.
  • A sharp goal brief from your workbench is the cheapest way to save quota: fewer stuck tasks means fewer triage wakes.

What it can and can't do

In headless mode Claude gets a pinned tool list. It can read the repo, edit task files and NOTES.md, run runner.sh and orchestrate.sh, and use read-only git. It cannot edit source code, commit, merge into main or push. Merging the agents branch into main stays with you. To drive a pass yourself, run /orchestrate in Claude Code; /plan and /signoff still work on their own.

Meta-orchestrator across your repos

The kit's limits are set per repo. With four repos on one machine, four loops share one Pro plan, one Go pool and one GOAT pool, and nothing in the kit sees the total. dsh's job at this level is to keep the total sensible, by choosing what each repo works on and when.

The backlog

One file, ~/code/ops/backlog.md, lists every goal across the four repos. You own the order; dsh owns the timing.

How dsh decides

  • It runs as a scheduled task, for example at 08:45, 12:45, 16:45 and 20:45. It reads each repo's goals and task status, today's runs.csv totals and recent pauses in fallbacks.log.
  • A repo is idle when it has no goal in progress. At most one active goal per repo.
  • It queues the highest-priority ready item whose repo is idle and whose after item is done.
  • It queues at most two new goals per day across all repos, since each one triggers a Claude plan wake, the largest wake there is.
  • Only one risky goal runs at a time across all repos, because risky goals sign off every task with Opus.
  • It holds new goals when fallbacks.log shows Go pauses in the last two hours, or when today's GOAT total is close to its share.
  • Every decision goes into the digest with its reason: "queued G-004 in dashboard-1; held portfolio item 7, Go pool paused at 14:10".

Limits of this layer

  • dsh only decides what and when. Planning, triage and sign-off stay with Claude inside each repo.
  • It can't stop work already running; it can only hold the next goal. To stop a repo now, stop its tmux loop.
  • If dsh is down, nothing new is queued and each repo finishes what it has. That fails safe.
  • Its decisions use DeepSeek, so they are scheduling calls, not quality calls. Anything about whether code is good stays with the gates, the reviewers and Claude.
  • Start it only once a second repo has the kit installed and a few goals have run cleanly in each. Until then, the control desk on its own is enough.

Setting it up

  • Add 9router as a custom provider: base URL http://127.0.0.1:20128/v1, protocol openai-completions, your 9router key. dsh fills the model list from 9router. Don't add a DeepSeek API key; that bills outside your plans.
  • Use DeepSeek V4.1 Flash on GOAT (cmc/) day to day. When the Go pool's five-hour window fills, every Go model stops, and your chats shouldn't be what pauses the workers.
  • Make ~/code/ops the control workspace (workspace-write): kitctl, repos.txt (repo names and paths), briefs/, prompts/, templates/, digests/. Open each repo as its own read-only workspace for drafting. Never use full access, and avoid the minimal profile because its file editor ignores the sandbox.
  • Run it in its own tmux window next to the loop: tmux new -s dsh 'npx @deepseek-ai/dsh web --no-open'. Scheduled reports only run while dsh is running. It needs Node 22.19 or later.
  • It listens on 127.0.0.1:3080 only. Keep it that way.
  • Test before trusting it. dsh's sandbox has no per-command allow-list, so kitctl is the guard. From dsh, queue a throwaway goal through kitctl, then ask dsh to edit a source file in the repo and confirm it is refused. If the sandbox also blocks kitctl from writing the goal file, widen the workspace to ~/code and rely on kitctl plus the morning summary, which flags any uncommitted change in a main checkout.

What it doesn't do

  • It never calls Claude. Its Claude Code subagent stays off; Claude is woken only by orchestrate.sh, inside its caps. Queuing a goal is how dsh asks for Claude's time.
  • It never writes task files or code. The runner builds any queued task file, so one written by dsh would skip Claude's planning.
  • It doesn't review or sign off pipeline code. It runs on DeepSeek, which builds most of your code, and reviewers must come from a different family.
  • Its usage isn't in runs.csv, so the kit's GOAT cap can't see it. Keep Sol and Kimi critiques occasional and check the GOAT console now and then.
  • It is a release candidate (0.1.0-rc) with breaking changes announced. If it breaks, run the same commands yourself; the pipeline doesn't wait on dsh.

Habits that pay off

  • Keep one brief template and improve it. Sharper briefs mean fewer retries and fewer Opus wakes, the biggest saving in the whole setup.
  • Before trusting a brief, open the session's step view and check that dsh read the files and functions it names. Guessed names in acceptance criteria are a common reason tests fail.
  • When a goal goes badly, give dsh the stuck tasks' digests and ask what in the brief caused it. Fold the answer into the template and add a line to NOTES.md yourself.
  • Read kitctl.log once a week. It is the record of everything dsh did to the pipeline.

Design lane: Google AI Pro

Visual QA today checks screenshots against a text brief, so it catches overflow and overlap but not "this isn't what I wanted". The design lane gives every UI goal a picture to build to and be checked against. It runs on your Google AI Pro subscription, so it spends none of your pools or Pro quota.

  1. Prompt. dsh writes the Gemini prompt from the repo: existing components, Tailwind tokens and the data the screen shows.
  2. Mockups. Nano Banana Pro edits a screenshot of the current screen ("add a filter bar above the table, keep everything else"), which stays far more consistent with your app than a blank page. Make two or three variants and pick one.
  3. Spec. Gemini 3.8 Flash writes the UI spec from the chosen mockup: layout, components, loading, empty and error states, tokens. Save the image to docs/design/ and the spec to docs/ui-spec.md.
  4. Brief. dsh turns the spec into the goal brief, with design: docs/design/<name>.png.
  5. Build. The pipeline runs the ui tasks, and visual QA compares its screenshots with the mockup as well as the brief.
  6. Review. After the milestone merges, give Gemini 3.8 Flash desktop and mobile screenshots plus the mockup. Its findings become the next brief.
  • The mockup sets the direction; the spec is the source of truth. Generated images can garble small text and exact sizes, so visual QA ignores exact colours and copy.
  • Design sessions move out of Claude Code, which saves Pro quota every UI milestone. Claude Code stays for structural decisions.
  • Use Gemini 3.8 Flash, the Gemini app's default on AI Pro, not 3.1 Pro: it is newer and ahead on most benchmarks, multimodal included. It is the same model as the pipeline's visual QA, which is fine because Gemini never writes your code.

What happens to each task

Three agents build in parallel. The tests must fail on the old code before they count, the gates check tests, scope and security, and a reviewer from a different model family reads every change. Anything that fails climbs the retry chain on the right, and if the whole chain fails, the orchestrator decides what happens next.

Profiles

One switch changes how much checking the pipeline does. Set the repo's usual profile in routing.sh, override it for a single run with PROFILE=fast .agents/runner.sh run, for one task with profile: risky in its front matter, or for a whole goal with orchestrate.sh goal "…" risky (or ask dsh to queue it as risky).

Running it on your Mac

The kit's scripts run on macOS as they are. What matters is the setup around them.

  • Install with Homebrew: brew install bash coreutils jq tmux gh node gitleaks semgrep ripgrep. Coreutils provides gtimeout, which the kit needs. Put /opt/homebrew/bin first in your PATH; which bash should show /opt/homebrew/bin/bash.
  • Start the loop with tmux new -s agents 'caffeinate -is .agents/loop.sh' so the Mac stays awake while it runs. Keep it on power; closing the lid on battery still puts it to sleep.
  • Use loop.sh, not cron. Claude Code keeps its login in the macOS Keychain, which cron jobs often can't read, so the orchestrator's wakes would fail.
  • Keep repos in ~/code, outside iCloud-synced Desktop and Documents folders. Sync fights with git worktrees.
  • 9router listens on 127.0.0.1:20128 directly, with nothing to forward.
  • Add .DS_Store to .gitignore in the kit repo and in each project repo.
